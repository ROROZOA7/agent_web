# v0.1 Build Definition: Agentic E-Commerce Assistant

Status: **Draft — pending user confirmation.**
Date: 2026-09-23
Scope authority: `docs/product/overview.md` (Confirmed v0.2)

## 1. What This Document Is

`docs/product/overview.md` defines *strategic scope* — stack, contracts, and
the five confirmed v0.1 decisions. It is not implementable on its own: it does
not say where data comes from, what each action accepts and returns, or how a
user observes success.

This document defines **what must exist and how its behavior is observed**. It
deliberately does **not** order the work. Sequencing belongs in a separate
execution plan created only after this definition is confirmed.

Nothing here overrides `docs/product/overview.md`. Where this document adds
detail, it must remain consistent with it.

## 4. Action Contract

Actions are the single authoritative operation path (`overview.md` §2). Every
action is server-side validated and authorized, and is surfaced to the agent
tool, React hooks, HTTP, CLI, MCP, and A2A by the framework.

The action ids below are **not free choices**: `lib/jev.ts` `SUGGESTED_ACTION`
already routes triage verdicts to these exact names. Renaming one requires
changing that committed map.

| Action | Purpose | Mutates | Approval |
| --- | --- | --- | --- |
| `triage-message` | Classify an inbound message; exists and is tested | no | no |
| `search-products` | Semantic product retrieval, Jev-reranked | no | no |
| `get-product` | Single product for PDP rendering | no | no |
| `get-cart` | Current cart contents | no | no |
| `add-to-cart` | Add a product to the cart | yes | no |
| `update-cart-item` | Change a line quantity | yes | no |
| `remove-cart-item` | Remove a line | yes | no |
| `get-order-status` | Fulfillment state of one owned order | no | no |
| `create-return-request` | Create a pending return request | yes | **yes** |
| `support-handoff` | Structured escalation with context | yes | no |
| `off-topic-handoff` | Decline politely, stay in domain | no | no |
| `clarify-message` | Ask one disambiguating question | no | no |

Every mutating action must be authorized against the authenticated session and
must reject any attempt to read or mutate another user's cart, order, or
return. Ownership is enforced server-side, never by UI filtering.

## 5. Data Ownership

App tables are owned by this application and seeded with demo data. Adapter
boundaries must keep persistence swappable for a real commerce backend later
(confirmed input #1), so query logic lives behind a module seam rather than
inline in actions.

| Entity | Key fields | Notes |
| --- | --- | --- |
| `product` | id, slug, title, description, price, currency, image, status, embedding | Embedding column requires the vector type |
| `order` | id, owner, placed_at, status, total | Seeded per demo user |
| `order_item` | id, order_id, product_id, title snapshot, qty, unit_price | Title/price snapshotted at purchase time |
| `cart` | id, owner, updated_at | One active cart per authenticated user |
| `cart_item` | id, cart_id, product_id, qty, unit_price | Unique per (cart, product) |
| `return_request` | id, order_id, order_item_id, owner, reason, status, created_at, decision record | Status is `pending` in v0.1 and never advances automatically |

The `return_request` decision record must persist the Jev verdict that gated
it — chosen label, confidence, probabilities, and threshold — so an approval
can be audited after the fact.

`application_state` (navigation, selection, `__url__`) stays owned by
Agent-Native and must not be duplicated by these tables.

## 6. Surfaces

Assistant-first (confirmed input #3): the assistant is the primary entry point
and storefront views are reachable through it. One contract owns each surface;
surfaces never mix channels mid-session (`overview.md` §4).

| Surface | Contract owner | Must render |
| --- | --- | --- |
| Assistant panel | A2UI for constrained panels; MCP Apps for rich content | Conversation, result panels, confirmation prompts |
| Product list (PLP) | A2UI | Ranked results, empty state, refine affordance |
| Product detail (PDP) | MCP Apps | Full description, media, add-to-cart affordance |
| Cart | A2UI | Line items, quantities, totals, empty state |

## 7. Journeys And Acceptance Criteria

A journey passes only when observed through the real interface. Plans and
completion messages do not count as proof (`docs/WORKFLOW.md`).

### J1 — Search → PDP → cart

1. An authenticated user asks for a product in natural language.
2. `triage-message` returns `product_search` above threshold.
3. `search-products` returns ranked results rendered as an A2UI PLP.
4. Selecting a result opens the PDP through MCP Apps with full detail.
5. Adding to cart updates the cart surface and persists across reload.

Accepted when: a natural-language request reaches a populated PLP; the PDP
renders the selected product; the cart reflects the added line after a full
page reload; and a second user cannot observe that cart.

### J2 — Gated return request

1. An authenticated user asks to return an item from an existing order.
2. `triage-message` returns `returns_refund` above threshold.
3. Eligibility is checked against an owned, returnable order item.
4. The Jev policy gate (#2) evaluates the request.
5. The user is shown an explicit confirmation naming the item and reason.
6. On confirmation, `create-return-request` persists a `pending` record.

Accepted when: no return record exists before explicit confirmation; the
persisted record carries the Jev decision; an ineligible or unowned item is
refused with a stated reason; and declining the confirmation leaves no record.

### Reachable but not acceptance-gated

Triage can emit `order_status`, `order_modification`, `support`, and
`off_topic`. Each must reach a defined, non-dead-end response. Order
modification is out of v0.1 scope, so `modify-order` has no implementation —
see §11 gap G1.

## 8. Jev Decision Services

In scope: #1 triage, #2 policy gate, and #3 next-action ranking, per confirmed
input #7. Services #4 model routing and #5 tool-risk gating are out of v0.1.

All Jev use must obey `overview.md` §5: one request per decision set, no
secrets in transmitted state, thresholds configurable per service, escalation
below threshold, and no retry budget spent on re-asking Jev.

Service #4 would conflict with pinning a single chat model, per confirmed
input #5, and that conflict is why it is excluded.

## 9. Search And Embeddings

Semantic vector search with **no keyword fallback** (confirmed input #6).

- Retrieval: pgvector similarity over product embeddings.
- Reranking: Jev service #3 reranks the retrieved candidate set.
- Embeddings: an OpenRouter embedding model, reusing `OPENROUTER_API_KEY`.

Because two non-deterministic layers sit on this path, acceptance tests must
assert **ranking quality** — the expected product appears within the top N —
not exact ordering. Offline tests must stub the embedding and Jev transports
the way `lib/jev.test.ts` already stubs the Jev transport, so the suite stays
runnable without network access or an API key.

## 10. Cross-Cutting Behavior

Every surface must define loading, empty, error, and timeout states. The
following are behavioral requirements, not implementation hints.

- Jev unavailable or below threshold must never silently act. Triage falls
  back to `clarify-message`; the returns gate fails closed.
- Embedding or vector failure on `search-products` must surface an explicit
  error state. With no fallback path, search is unavailable rather than
  degraded.
- WebMCP must detect support and select the non-WebMCP path when unavailable;
  the fallback is mandatory, not optional.
- Agent-rendered A2UI and MCP Apps output is untrusted: sanitize, enforce CSP,
  verify `postMessage` origin, never wildcard.
- New user-facing strings need all 11 locales, or a stated policy for
  English-only v0.1 strings.

## 11. Gaps Requiring A Decision Before Implementation

These are unresolved. None may be answered by assumption.

- **G1 — `modify-order` has no owner.** `lib/jev.ts` routes the
  `order_modification` intent to a `modify-order` action, but order
  modification is out of v0.1 scope. Either that intent routes to
  `support-handoff` in v0.1, or the routing map changes. Both alter committed
  behavior in `lib/jev.ts`.
- **G2 — `order_status` is reachable but not acceptance-gated.** Returns
  already require order retrieval, so the data exists. Whether `get-order-status`
  is a first-class journey or a minimal read is undecided.
- **G3 — App-table migration tooling is absent.** `drizzle-kit` is not
  installed and no `db:migrate` script exists, yet `migrate-production.ts`
  expects app tables from `drizzle/schema.ts`. The authoring and apply path
  must be chosen.
- **G4 — pgvector availability in production is unverified.** PGlite 0.5
  dropped the bundled `/vector` export; it now requires
  `@electric-sql/pglite-pgvector` (`0.0.9`, pre-1.0). Production Postgres
  additionally needs `CREATE EXTENSION` privilege. With no fallback selected,
  a host lacking pgvector blocks deployment.
- **G5 — The pinned chat model is unnamed.** An exact model id is required for
  reproducible acceptance tests.
- **G6 — Assistant contract routing rule is unspecified.** The rule choosing
  A2UI versus MCP Apps per view inside the assistant panel, without mixing
  channels mid-session, is undefined.
- **G7 — Demo seed identity is undefined.** Seeded demo users, their orders,
  and how a tester authenticates as one are unspecified, yet J2 depends on an
  authenticated user owning an existing order.

## 12. Out Of Scope For v0.1

Order modification; refund or money movement; return approval or label
generation; Jev services #4 and #5; anonymous shopper sessions; pricing and
billing; DOM automation.

## 13. Validation Strategy

- Focused tests for decision logic and eligibility rules, with stubbed
  transports, following `lib/jev.test.ts`.
- Integration tests for action authorization and ownership boundaries.
- End-to-end interaction for J1 and J2 through the real interface.
- Ranking-quality assertions for search, never exact-order assertions.
- Repository checks: `pnpm test` and `pnpm typecheck` must pass.
